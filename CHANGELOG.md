# Changelog

All notable changes to Cascadia PLM will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- **The Docker environment example lists the RabbitMQ credentials.** `RABBITMQ_USER` and `RABBITMQ_PASSWORD` were the only Compose variables the example omitted, leaving the broker on its built-in default with nothing in the checklist to say so.
- **LLM token usage is now recorded.** Every AI chat request writes one `ai_usage_logs` row with the request's summed prompt/completion tokens, provider, model, duration, and — new on the table — the program the session was scoped to, which is what a future per-program budget sums over. A provider that reports no usage yields a visibly unmetered row (null counts) rather than a silent zero. Tool-audit rows now carry the program as well.
- **AI spend can now be capped.** An admin can set `monthlyTokenBudget` on any AI settings scope: on a program's settings it bounds that program's month-to-date token spend (summed from the usage ledger), on the global settings it bounds the whole instance's. Every AI surface — chat and enrichment — resolves its provider through the same chokepoint, so a reached budget answers 429 everywhere at once; the in-flight stream that crosses the line finishes and is recorded, so an overrun is at most one request. Separately, one user can no longer hold unbounded concurrent chat streams: a per-user cap (default 3, `AI_MAX_CONCURRENT_STREAMS`) answers 429 while the user's slots are full, and a slot frees the moment its stream ends, however it ends.
- **The maintenance jobs actually run now.** Session cleanup and thread-cache cleanup were fully defined — configs, handlers, 'recommended to run daily via a scheduler' — and had zero submit sites, so neither had ever run. The jobs worker's scheduler loop now checks every ten minutes (`JOB_MAINTENANCE_SWEEP_MS`) and submits each maintenance job whose type has no active run and none within its period (`JOB_MAINTENANCE_PERIOD_MS`, default daily). System-submitted rows carry no user: `jobs.created_by` is now nullable, which is the migration this release note rides on.
- **Firmware images can be attached to items.** `.bin`, `.hex` and `.elf` were missing from the vault's allowed-extension list, so the compiled artifacts a firmware or software item exists to carry were the one thing that could not be uploaded to it. Contributed by [Artur Klujewski](https://github.com/Kujoo25) in [Cascadia-App#86](https://github.com/Cascadia-PLM/Cascadia-App/pull/86)

### Fixed

- **The sidebar no longer offers a page this edition does not have.** One entry under Designs pointed at a route that ships in a separately licensed module, so following it fell through to the design detail route, which asked the API for a design named after the path segment. Five `/api/v1/designs/:id` handlers passed that segment straight into a query, making the result an unhandled 500. The entry is gone, and those handlers now answer 400 for an id that is not a UUID. Contributed by [Artur Klujewski](https://github.com/Kujoo25) in [Cascadia-App#83](https://github.com/Cascadia-PLM/Cascadia-App/pull/83)
- **Work-instruction step and operation edits now show what the server has.** The detail page kept its own copy of the steps and operations and patched it after each write, so a concurrent edit never appeared; and the operation editor's own writes refreshed nothing at all, leaving a rename, reorder or deletion invisible to every other view of the same template. Both now read from the shared cache. Finishing an edit session also refreshes the branch and item lists, so a branch picker no longer offers the working branch that cancelling the checkout just deleted.
- **The upstream-changes banner's Dismiss All button works.** It had no handler at all, and a second button beside it pointed at a backend that was never built — that one is gone. The banner also no longer renders as though there were no upstream changes when the check for them fails; it says the check failed and offers a retry.
- **A broken Docker image build is now caught in CI.** Nothing built the images, so a workspace deleted in one change left both Dockerfiles referencing a directory that no longer existed and neither image could be built at all — discovered only by someone trying. CI now builds the dependency stage of both images on every change, and each Dockerfile lists its workspace manifests once rather than twice, so the two copies can no longer drift apart.
- **Two people checking in the same vault file at once can no longer leave it with two current versions.** Creating a new version demoted the old one, stored the bytes, and inserted the new row as three separate unguarded steps, so two writers could interleave into two rows both claiming to be the latest and sharing a version number. The demote is now a single conditional write inside one transaction with the insert, and the loser is refused cleanly. Two defects found alongside it are fixed too: a superseded version no longer keeps a check-out lock that nothing could ever release, and a storage failure part-way through can no longer leave a file with no current version at all — the bytes are stored before anything is demoted.
- **The Python CAD workers enforce their job timeout.** `JOB_TIMEOUT` was a setting nothing read, so a conversion wedged in a native geometry call held its worker slot indefinitely while the worker still reported itself healthy. A job past its deadline is now failed and retried like any other failure, and a worker still stuck after `POISON_EXIT_GRACE_MS` restarts itself rather than losing the slot permanently.
- **Editing a design's structure refreshes the other views of the same data.** Adding a part, removing one, or pulling in a cross-design reference left the parts lists, relationship panels and mBOM views showing the old structure until the browser was reloaded. They now update with the edit, and a structure edit that fails reports an error instead of silently doing nothing.
- **Deployment documentation no longer teaches `db:push` for production databases.** The cloud-database and orchestration guides instructed operators to create and repair live databases with the schema-diff tool, which is a development convenience and not the upgrade path. They now teach the committed-migration path, and the troubleshooting entry for a refused start names the one-time `db:baseline` stamp a pre-v0.5 database needs instead of the destructive workaround it used to suggest.
- **Link enrichment records its LLM token usage,** so the tokens it spends count against the monthly token budget instead of escaping it.
- **Checking out a file in the vault now takes its edit lock atomically.** The lock was claimed by reading the file, deciding in application code that nobody held it, and then writing the claim unconditionally — so two people checking out the same file at the same moment could both be told they held the exclusive lock, and the second write silently replaced the first. The claim is now a single conditional write: the loser gets the usual "already checked out by …" refusal, and an expired lock is released only while it is still expired.
- **Concurrent commits on one branch no longer orphan each other.** Two commits landing on the same branch at once both read the same branch head, both parented on it, and the second head update overwrote the first — leaving the first commit unreachable from the branch's history while its rows sat in the database. The head is now read under a row lock, so the parent it hands out and the head it later writes cannot be separated by another commit. A merge commit created outside the release path had the same defect one level up: its branch read sat outside the retry, so a retry parented on the head it had already superseded.
- **Two change orders releasing the same item can no longer both assign its revision letter.** Releasing a change order whose work is not on a branch ran at the database's default isolation with no retry, unlike the branch merge, which has run serializable with a bounded retry since it was hardened. The two branchless passes now run under the same isolation and the same retry, and the revision counter they report is accumulated per attempt so a retry cannot inflate it.
- **A database outage no longer crash-loops the jobs worker or loses the jobs in flight.** Claiming a job and marking one failed both talked to the database outside any error containment, and the consume callback discarded the promise — so a transient outage ended the process with an unhandled rejection and restarted it into the same failure for the outage's duration, acknowledging deliveries away as it went. A claim that fails now pauses briefly and returns the delivery to the queue; a failure that cannot be recorded still acknowledges and leaves the row for the stale-job sweep to recover; and a message that is malformed, or whose payload does not match its job type, is rejected at the boundary instead of reaching a handler.
- **A Python CAD worker no longer discards a job when the database blinks.** A transient error while claiming a job was caught by the same handler that marks a job failed — which does nothing to a job that is still queued — and the delivery was acknowledged regardless, so the job's only message was consumed and the row sat queued forever. A failed claim now returns the delivery to the queue, and a message the worker cannot parse goes to the dead-letter queue rather than being dropped.
- **Failed pull-from-main and rebase requests answer with the documented error envelope.** Both returned a bare string under `error`, so a client reading `error.code` or `error.message` off the response got `undefined` and an empty message. They now carry the standard envelope with a code, a message and the request id; a rebase that needs manual resolution answers 409 with its field conflicts alongside.
- **The same person can no longer be added twice as an approver on a workflow state.** Nothing constrained the approver tables, so a repeated assignment inserted a twin row — invisible in the gating arithmetic, which collapses the pair, but visible in the approver list, and removal deletes by row id, so removing an approver left the twin still approving. Both tables now reject the duplicate. **Upgrade note:** existing duplicates are collapsed by the migration, keeping the required assignment where the pair disagreed.
- **Kubernetes deployments now apply database migrations.** Nothing on the Kubernetes path migrated at all — the pods run the server directly, and the migrate-on-startup behaviour is a Compose-only wrapper — while the deployment guide claimed the application did it on startup. A `cascadia-migrate` Job now ships with the manifests, with the install and upgrade sequences documented; it is deliberately outside the kustomization, because a Job's pod template is immutable and an upgrade has to replace it.
- **An item on a change order can be rebased onto main again.** Rebasing a working copy, or pulling main's changes into it, always inserted a _new_ version row carrying the branch's working revision — and an item added to a change order already has one, because the working copy is created the moment it is added. The insert collided with the uniqueness constraint on (item number, revision, design, type), so the whole recovery rolled back and the user saw a duplicate-key error: in the ordinary case, neither operation could succeed at all. Both now update the working copy the branch already has, leaving its files, its BOM edges and its identity where they are, and repointing only the base it was taken from. A plain checkout, whose branch row still points at the released version, still mints a copy as before.
- **A traveler run can no longer be opened twice at once.** Starting a run on a work-order instruction checked for an open run and then created one, with nothing between the two steps — so two requests arriving together both created one, and the line's completion tally counted a single physical run twice against the number of runs the line requires. That tally is what gates completing the work order. The database now enforces one open run per technician per line per unit, and a request that loses the race is handed the run that won rather than an error. `instruction_executions.status` is also constrained to its six legal values, since anything else silently fails to count. **Upgrade note:** the migration abandons any duplicate open runs it finds — keeping the newest of each group and marking the rest `Incomplete` with a completion time of now — and refuses to apply if any run holds a status outside the six.
- **Adding a relationship through the type chooser works again.** The dialog sent an explicit `null` for an empty reference designator or find number, and the route's body schema — which takes both as optional — rejected it, so the ordinary case (leave them blank) answered 400 with a validation error naming fields the user never filled in. The fields are now omitted rather than nulled.
- **A document larger than 2 GB no longer overflows its recorded size.** `documents.file_size` was a 32-bit integer while the vault's own size column is 64-bit, so a Document item recording a file above 2 GB failed on the size column. It is now `bigint`, matching the vault.
- **A released item list no longer reports itself empty past the first page.** Version resolution decided whether the commit graph held a design's contents by asking whether the query it had just run returned any rows — so paginating past the end, or applying a filter nothing matched, looked identical to missing commit data and sent the request on to a fallback that answered from a different source, reporting a total of zero for a design holding hundreds of items. The test is now the count before pagination, which is the question that was meant to be asked.
- **Listing items at a commit, tag or branch no longer loads the whole design into memory.** Resolving which version of each item was current at a commit — the ancestry walk, the filters, the count and the page — now happens in one query, and the branch view's overlay of a branch's own versions onto main's contents in one more. A fifty-row page of a 400-item design resolves about 3.5x faster and no longer grows more expensive with the size of the design rather than the size of the page. Pages are also ordered now: `limit`/`offset` used to slice a set the database returned in no particular order, so an item could appear on two pages or none.
- **A failure outside the database is no longer reported as a database failure.** To classify a constraint violation, the API error handler reaches past the query wrapper to the driver error underneath, and that walk matched anything carrying a string `code` — which Node's filesystem errors and the HTTP client's socket errors both do. A missing vault object or a refused message-broker connection therefore came back as `DB_QUERY_FAILED`, "Database operation failed", and was logged CRITICAL against a database that was never touched. A failure is now classified as a database error only when its code has a SQLSTATE's shape; anything else answers `INTERNAL_ERROR` and "An unexpected error occurred", which is honest about not knowing rather than naming a subsystem it never reached.
- **The versioning graph is now referentially enforced.** Commits, branches, branch tracking rows, item versions, and conflict acknowledgments all carry real foreign keys: deleting a commit out from under its children is refused, deleting an item a live branch still tracks is refused, and deleting a workspace branch no longer leaves tracking rows pointing at deleted items. A commit's pointer to the change order that produced it is enforced too, with `ON DELETE SET NULL` rather than a refusal: a release commit is history and must outlive the change order that made it, so removing the change order clears the attribution and leaves the commit chain intact. A new `npm run db:check-orphans` reports any dangling versioning references per edge before an upgrade. **Upgrade note:** the migration cleans the inert orphan classes itself, but a dangling commit parent or branch pointer aborts it on purpose — that is history corruption; run the orphan check and involve a human before retrying.
- **Design lineage pointers are now real foreign keys.** The links a design carries to its family parent, clone source, MBOM derivation source (design, tag, commit), and default branch were unvalidated ids; the database now enforces them. Deleting a source Engineering design clears a derived MBOM's provenance pointer instead of blocking the deletion, and the migration nulls any pointer whose target row no longer exists before validating.
- **The database now rejects corrupt revision markers and unknown merge statuses.** A revision starting with `-` must be one of the two legal working-marker shapes (`-` or `-` plus eight hex characters), and a change order design's merge status must be one of `pending`/`merged`/`conflict`/`skipped` — a malformed marker used to make the release machinery mint a revision from the literal marker text, and a typo'd status silently skipped or double-merged a design. **Upgrade note:** the migration validates existing rows and aborts if violations exist; scan first with `SELECT id, item_number, revision FROM items WHERE revision LIKE '-%' AND revision <> '-' AND revision !~ '^-[0-9a-f]{8}$'` and the matching merge-status query from the release notes.
- **The items grid and the item detail page can no longer disagree about the current revision.** Both now resolve versions in commit-ancestry order. Previously the grid sorted candidate rows by creation time, which served the wrong revision after an ECO promoted a working copy in place — the promotion keeps the row's original creation time while its commit moves ahead, so the grid showed another change order's earlier release while the detail page showed the promotion. Version resolution and the released-version fallbacks are also fully ordered now, so repeated reads return the same row instead of whatever the storage engine surfaced first.
- **The release preview now shows the revision letters the release will assign.** For revise and promote affected items, the preview preferred the revision predicted when the item was added to the change order — stale the moment another release moved the same item. It now computes a revise the way the merge does and resolves a promote through the lifecycle mapping, so what a reviewer approves is what the release assigns. A promote whose lifecycle resolves to no target no longer appears in the preview at all — the release skips it, so previewing it was a false promise.
- **A role can no longer be assigned to the same user twice.** `user_roles` had no key at all, so a repeated assignment quietly inserted a twin membership row. It now carries a composite primary key; the write paths treat a repeat as a no-op, and a duplicated role id in one assignment request is collapsed instead of failing with a misleading "Role not found". The migration removes any pre-existing twin rows before the key lands.
- **Two design-less items can no longer share one identity.** The items uniqueness constraint (`item_number`, `revision`, `design_id`, `item_type`) never fired for item types that carry no design — work orders, tools, physical parts, tasks, issues, change orders — because SQL treats two NULL `design_id`s as distinct. It is now `NULLS NOT DISTINCT`, so a second `WO-000123` is rejected instead of silently created. **Upgrade note:** the migration validates existing rows and refuses to apply while such twins exist — run `npx tsx scripts/check-items-duplicates.ts` first; it names every colliding row.
- **Long CAD conversions no longer die to broker heartbeat timeouts.** Both Python workers ran the whole conversion inside pika's consume callback, so a job outlasting the 60s heartbeat starved the I/O loop: RabbitMQ closed the connection and redelivered the job mid-run, doubling work and failing runs that were about to succeed. Deliveries now execute on bounded worker threads while the connection thread keeps pumping heartbeats; acknowledgements are marshalled back through pika's one thread-safe entry point, and each worker thread gets its own database connection.
- **The jobs worker notices when it loses RabbitMQ.** A dropped broker connection used to leave the worker idling forever on a dead channel while its `/health` endpoint kept answering 200. The worker now reconnects with capped backoff (1s → 30s), exits 1 once the broker has been unreachable past `WORKER_RECONNECT_DEADLINE_MS` (default 5 minutes) so the container restart policy takes over, and `/health` answers 503 `{"status":"disconnected"}` while the link is down. Acknowledgements are now scoped to the channel a message arrived on, so a reconnect can no longer tear down the new consumer with a stale delivery tag.
- **Configured job retries now actually run.** A failed job was parked for retry with a next-retry timestamp — and nothing ever re-published it, so the first failure was terminal regardless of `maxAttempts`. Every Node jobs worker now sweeps the parked rows on an interval (`JOB_RETRY_SWEEP_MS`, default 15s) and re-publishes the due ones. The same sweep recovers a job whose submission was interrupted between the database insert and the queue publish, which previously stranded it invisibly forever.
- **A job delivered twice no longer executes twice.** RabbitMQ promises at-least-once delivery — a connection drop or a retry re-publish can hand the same job to two workers — and execution started with a read-then-write, so both ran it. Workers (Node and both Python CAD workers) now take an atomic claim: the second delivery finds nothing to claim and acknowledges without executing. `attempts` now counts executions started (claim time) on both sides of the system; previously the TypeScript side counted failures instead, so a job's attempt count could disagree with how many times it actually ran.
- **Two users checking out the same item at the same moment no longer both "win".** Checkout acquisition is now compare-and-set: the loser of either race path — both creating the working copy, or one claiming while the other creates — gets a friendly conflict answer instead of a duplicate working copy or a raw database error.
- **Two ECOs releasing the same item can no longer overwrite each other.** The concurrent-modification check ran only before the merge transaction opened, so a release that landed in the gap — or at the same moment on another connection — was silently superseded by the stale branch's content, and the loser of a truly simultaneous pair surfaced as a raw database error. The check now re-runs as the first statement inside the merge's serializable transaction, and the losing release fails with a merge-conflict error naming the affected items. A release retried after a serialization conflict also now reports its work once — revision counts, item changes, and the notifications sent to derived MBOMs were previously accumulated across attempts.
- **Malformed JSON in a request body answers 400, not 500.** A body that failed to parse used to surface as an internal error; it now returns 400 in the documented error envelope, naming the parse failure.
- **A user can no longer hold two active approval votes on one workflow state.** `workflow_approval_votes` enforces one active vote per (instance, state, user) — a second active vote is rejected where it previously accumulated silently — and the migration collapses any pre-existing twins.
- **Failed Python CAD jobs park for retry again.** The Python workers' retry parking crashed on a psycopg INTERVAL placeholder, so a failed conversion never entered the retry lane at all; the query is fixed and the parked status unified to `pending` across the TypeScript and Python sides.
- **The work-instruction traveler runner talks to the API reliably.** Its bespoke fetch layer is replaced with the shared `apiFetch`: request failures surface to the operator instead of vanishing, React StrictMode no longer double-starts a run, and completion no longer sticks in a blocked state.
- **Error responses match the documented envelope again.** Three drifted shapes — the CSRF rejection, `at-context` resolution errors, and several hand-rolled admin 400s — are back on the `{ "error": { ... } }` envelope the API documentation promises.
- **Cancelling a job now actually stops it.** Cancel accepts running jobs (previously refused): the row flips to `cancelled` immediately and every worker — Node and both Python CAD workers — notices at its next progress checkpoint and aborts its handler. A job's terminal state is now immutable: the completion/failure marks are guarded to running rows, so a handler that outlives its timeout or a cross-process cancel completes into the void instead of resurrecting a settled job. Timeouts now abort the handler as well (previously the worker gave up while the handler kept running and its late completion overwrote the timeout failure), and each job type's configured `timeout` is enforced instead of the worker-wide default. One caveat, now documented: a handler that never reports progress is only stopped by its timeout.
- **The `none` revision scheme no longer hides the items it releases.** Items released under a lifecycle configured with the `none` revision scheme were assigned an empty revision, and an empty revision is what Cascadia treats as an unreleased working copy — so those items were released in name but filtered out of every query that answers "what is released", including released-item resolution and design baselines. Released items under `none` now carry a fixed `N/A` revision that never advances, and reads as released everywhere. Saving a lifecycle is also now refused when `none` is set on an ECO-driven lifecycle: each release there creates a new version of the item, and two versions of one item cannot share a revision, so the configuration would have failed partway through a release. Per-phase `none` overrides are unaffected.
- **Item history now shows deletions instead of hiding them.** History for an item whose deletion had been released through an ECO was silently truncated: the read path filtered out soft-deleted rows, which discarded the merge commit recording the deletion — because that commit points at the very row the merge marked deleted — along with every earlier commit that touched the released row. In the checkout-without-edit case the timeline went empty entirely. Item history is now delete-inclusive, and opening the history of a deleted item by its own URL returns its timeline rather than a 404. Access is unchanged: the same design-membership check still gates the read.
- **Item history no longer records edits that were never applied.** Saving a checked-out item on a branch recorded field changes from the values submitted rather than from the values stored, so any field the item type does not actually persist — several are accepted by the API but have no column behind them — appeared in the commit history as a change, with a value no view of the item could show. History is now computed from what was written, so every recorded change is one you can find on the item. Part-specific fields (lead time, weight unit, cost currency, tracking mode) are also now categorised correctly as type fields rather than custom attributes.
- **A branch delete no longer takes another engineer's checkout, and a late delete no longer wedges an ECO at release.** Deleting an item on a branch cleared the exclusive checkout whoever held it was working under, and it never recorded the deletion on the owning change order — so a delete of an item the branch was not already tracking left content the affected items list could not show, and the release then refused the change order with nothing the user could do in the app. Deleting now refuses when someone else holds the checkout, naming the holder exactly as a contended checkout does; it is turned away up front once the change order's scope is locked, like any other way of bringing a new item onto the branch; and it lists the item on the change order as Obsolete so what merges and what reviewers approved stay the same set. Deletions are recorded whether or not the item's lifecycle configures an obsolete action.
- **A work order's first traveler run no longer fails when several technicians start at once.** Starting work on a `Not Started` order moves it out of its initial state, and that move read the workflow instance before creating or advancing it — so when several first runs landed together, one won and the rest came back with "already exists" or "concurrent transition" and recorded no execution at all. Putting an item in a lifecycle state now names the target state rather than a particular edge: if a concurrent caller already made exactly that move, the request succeeds as a no-op instead of failing. Genuinely illegal moves — a state the lifecycle has no path to, released lineage, or a change order sent to the item endpoint — are rejected exactly as before. The same fix removes a workflow-history entry that could record a state regression the item never actually made.
- **Search terms match the characters you typed.** `%` and `_` are SQL wildcards, and every search box, column filter and report filter passed your text through to the database unescaped — so a search for `A_1` also matched `AB1`, a report filtering on `50%` matched every row, and a bare `%` scanned the whole table. All of them now match those characters literally; substring matching is unchanged. Report filters whose value is unset now match nothing instead of filtering on the literal text "undefined", searching a design's items is now case-insensitive to match the same view's history, and a search term made only of punctuation no longer returns a server error.
- **PDF attachments now record their page count.** Uploading or checking in a file only ever recorded its extension, MIME class and detected category — the metadata extractor took the file's bytes and ignored them. PDFs are now read on upload and check-in, and their page count, title, author and producing application are stored alongside the rest. Extraction is decided by the file extension rather than the type the browser claims, skips files over 32 MB, and never fails an upload: a PDF that cannot be parsed lands with exactly the metadata it would have had before. Image EXIF and native CAD property extraction remain out of scope — converted CAD models already carry units, polygon count and bounding box from the converter.
- **Per-type retry delays now apply to CAD conversion jobs.** The Python workers parked every failed job on a hardcoded 30s/60s/120s backoff while the job type's own `retryDelays` said otherwise — CAD conversion asks for 60s/120s — so for every Python-executed type the configured schedule governed nothing. The schedule is now recorded on the job row when the job is submitted, alongside its attempt limit, and both the Node and the Python failure paths read it. Editing a job type's delays applies to jobs submitted afterwards, not to rows already queued, and the admin Retry button re-reads the current configuration; jobs queued before the upgrade keep the old built-in backoff until they drain.
- **An item created and then deleted on the same change order branch no longer keeps appearing in global search.** Its working copy is retired along with the branch's tracking of it, and the deletion stays in the item's history.
- **Hard delete no longer destroys evidence it should have kept.** Deleting a change order was offered on every row at every state and took the whole approval record with it — the workflow instance, its history and votes, and the affected and impacted item lists. `DELETE` now refuses an item in a released state, a change order past Draft, and a completed work order; cancel the change order through its workflow, or delete on a branch, where the deletion is itself recorded. A draft change order is still deletable, and the change-order list and detail page stop offering the action where the server would refuse it.
- **A change order's description is now stored.** The change order detail page has always offered an editable Description field, and the API has always documented it, but nothing persisted it — whatever was typed was discarded on save and gone on reload. `change_orders` gains a `description` column; existing change orders are unaffected and start with an empty description.
- **A requirement's type can now be set through the API under the name the API documents.** `PUT /api/v1/requirements/{id}` and `PUT /api/v1/items/{id}` accepted `requirementType` and silently dropped it; both now store it, and `type` — the name the column itself uses — is accepted alongside it.
- **Commit history now labels a type's own fields correctly for every item type.** The list of type-specific field names was maintained by hand and had drifted: it named five fields that exist on no table, omitted most of the ones that do, and covered none of Test Plan, Test Case, Work Instruction, Issue, Tool, Work Order or Physical Part, whose fields were all recorded as generic attribute changes. It is now read from each type's own table. Existing history rows are unchanged.
- **A failed item creation on a change order branch no longer leaves a half-made item behind.** Creating an item on a branch wrote the shared row and the type's own row in two steps, and only the first was inside the transaction — so a type handler that rejected the data left an items row with no Part or Document behind it: visible in search, impossible to open, and impossible to delete from the branch it was stranded on. Both rows are now written together, or neither is.
- **Issues are now scoped to the caller's programs and designs.** `GET /api/v1/items?itemType=Issue` admitted every issue in the instance to any authenticated caller holding `issues:read`, and the by-id routes passed the same rows unchecked. An issue is now reachable only through one of the three axes it actually carries — the design on its item row, its own program, or a link to a reachable design — on the item list, global search, by-filename lookup, dashboard counts, saved-report execution and file listing alike, and on `GET/PUT/DELETE /api/v1/issues/:id` plus every generic `/items/:id` sub-route.
- **A new issue takes its program from the designs selected on the form**, where those designs resolve to exactly one program. A Standard Library design, or a selection spanning two programs, derives nothing rather than guessing.
- **An issue carrying none of the three axes stays visible to administrators alone**, and `PUT /api/v1/issues/:id` (and `PUT /api/v1/items/:id`) now accept `programId` so such a row can be repaired. Setting a program is checked against membership of the destination program, and the generic item route now makes that check for work orders too, which previously only their own route made. Tasks are deliberately unchanged and stay visible instance-wide: nothing in the application supplies a task's program and nothing can derive one, so scoping them is a separate decision about requiring a program at creation.
- **Issues raised before that gate take their program from the designs they name.** The upgrade migration applies the same derivation to existing rows in both editions, ahead of the gate, so an install upgrading through here carries the repair before the predicate starts relying on the column. An issue that already names a program keeps it, one whose designs span two programs is left alone, and one linked only to the Standard Library derives nothing — those rows stay reachable by cross-program authority until an administrator names a program for them.
- **An administrator can release a file lock held by a departed colleague again.** `POST /api/v1/files/:fileId/force-unlock` charged `documents:manage` — an action no built-in role holds, and one a scoped API key cannot acquire either, since key scopes only narrow — so it answered 403 to everyone, Administrator included. The Force Unlock control it belongs to had never rendered, because no page passed the flag that showed it. The route now charges `documents:update` plus `system:manage` when the lock belongs to someone else, the same pair `POST /api/v1/items/:id/unlock` charges to break an item lock, and the control appears for anyone holding `system:manage`. Releasing a lock you hold yourself is unchanged, and so is program isolation. Previously the only recourse was the 24-hour checkout expiry. **Upgrade note:** a deployment-authored custom role holding `documents:manage` but not `system:manage` loses access to this route.
- **Detail-page fields are announced with their names again.** All six `ViewEdit` controls — the fields that carry most of the item detail pages — rendered their label as bare text beside the control, associated with nothing: a screen reader announced an unnamed textbox, and clicking the label did not focus the field. Text, textarea, number and currency fields now carry a real `<label for>`; the select and badge triggers are named with `aria-labelledby`, since `for` pointing at a `<button>` is unreliable across assistive technologies; and the unit and currency sub-selects, which have no visible label of their own, take their name from the field they belong to. The traveler runner's execution-data fields had the same defect on everything but the checkbox and are fixed the same way — its pass/fail pair, being two buttons with nothing for `for` to point at, becomes a named group instead.
- **`CORS_ALLOWED_ORIGINS` now works from a browser.** The setting was inert. The CORS preflight was answered inside the API handler wrapper, but route modules register concrete methods only, so Hono dispatched `OPTIONS` to no route at all — every preflight 404'd without a single `Access-Control-*` header, and the browser blocked the request that would have followed, whatever the variable said. `/api/*` now answers preflights directly, from the same origin policy that stamps the real response, so what a preflight advertises is what the response carries. An origin the policy does not list gets a 204 with no CORS headers and stays blocked.
- **A job whose worker dies mid-run is no longer stuck forever.** Only the worker executing a job ever moved it off `running`, so a worker lost to an OOM kill, an eviction or a power cut wedged its job there permanently — the claim refused to redeliver it, the retry sweep only ever looked at parked rows, and the admin Retry button only accepts failed ones. The jobs worker now also sweeps running rows (`JOB_STALE_SWEEP_MS`, default 60s) and fails any whose execution is past its type's own `timeout` plus a grace window (`JOB_STALE_RUNNING_GRACE_MS`, default 5 minutes), through the same guarded failure path a worker uses — so the job retries or fails terminally exactly as a reported failure would, and a worker that was merely slow and finishes during the sweep still wins. Rows of a job type this worker does not have registered are left for whichever worker fleet does. It expires a lease, not a process: a handler's side effects outside the jobs table must be idempotent or checkpointed.
- **An item can no longer appear twice on one change order.** Three paths put an item into a change order's scope — the Add dialog, checking an item out to an ECO, and every write that reaches an ECO branch directly — and each looked for the item, found nothing, and inserted, with nothing holding the two steps together. Two requests arriving together left the same item listed twice under two different actions, and the release then applied whichever row the database returned first. The database now enforces one scope row per item per change order: the registration paths treat losing the race as the no-op they already promised, and the Add dialog answers with the same "already an affected item" message it gives when it spots the duplicate itself. **Upgrade note:** the migration removes duplicates it finds, keeping the row that carries a working copy, then the oldest.
- **A job claimed or cancelled while it was being queued is no longer demoted back to `queued`.** The status flips that follow a publish wrote unconditionally, so a worker that claimed the job first, or an admin who cancelled it, could be overwritten — leaving the row at `queued` with its message already consumed, which nothing would have woken again. Every post-publish flip now names the status it expects and stands down when the row has moved on.
- **A job whose queue message vanished no longer sits at `queued` forever.** Nothing ever re-published a job in `queued` status: the atomic claim was the only thing that moved one, so a delivery a worker acknowledged without claiming — a transient database error on the claim path — or a message the broker lost took the job's last wake-up with it, and only an admin cancelling it ended the wait. The retry sweep now also re-publishes a `queued` row once it has sat longer than `JOB_QUEUED_STALE_MS` (default 10 minutes). The duplicate delivery a genuinely deep backlog costs is discarded by the claim, and each re-publish restarts the row's clock, so it costs at most one duplicate per job per window.

### Changed

- **The v0.5.1 upgrade is a single migration.** Everything this release changed in the database arrived as twenty-five migration files (nineteen in the community edition), none of which was ever in a release — v0.5.0 shipped with the baseline alone. They are consolidated into one `0001_remediation`, statement for statement in the same order, so the upgrade notes above still describe exactly what runs; a database that already applied the whole sequence skips the consolidated file rather than replaying it. CI now also checks that the committed migrations build the schema the code declares, by migrating one database and pushing another and diffing them — applying without throwing was never the same as arriving at the right schema. See [docs/deployment/upgrading.md](./docs/deployment/upgrading.md).
- **File-vault and session lookups hit narrower indexes.** The "latest version" and "primary model" flags on vault files were each indexed on their own — two-value indexes spanning the whole table, when every read asks the question per item. They are now partial indexes on the item id, about half the size and actually usable by those queries. `sessions.user_id` gained the index its two hot paths (list a user's sessions, log a user out everywhere) and the user-deletion cascade always needed; two indexes that served nothing — `items.is_current` and `branches.branch_type` — are dropped, each already covered by a composite the same queries use.
- **The item relationship graph loads in a bounded number of queries.** The walk behind the graph view used to issue roughly six queries per node, so a wide assembly neighbourhood took hundreds of round trips; it now batches each depth level, costing a handful of queries per level regardless of how many items the level holds. Repeated loads of the same graph also return byte-identical output — ordering used to depend on storage order.
- **Request bodies are now validated on the item and admin settings surfaces.** The generic item update (`PUT /items/:id`) runs the update schema of the item's own type — a type-invalid field is a 400 naming the field, and fields outside the type's schema (including server-managed ones) are stripped rather than silently written. Batch item operations, checkout/checkin, lock/unlock, transitions, property sync, and every admin settings write (AI provider config, component catalog, item-type configs, system settings, thread cache, API-key policy) validate the same way, and the OpenAPI spec now documents each of these request bodies — what the spec promises is what the route enforces.
- **Docker images build on Node 22 and pinned Python bases.** The app and jobs-worker Dockerfiles move from `node:20-alpine` (EOL April 2026) to `node:22-alpine`, matching the Node version CI and the compose stacks already run. The CAD converter worker's Dockerfile now pins its base images by digest (`condaforge/miniforge3:latest` and `debian:bookworm-slim` as resolved 2026-08-27), so a rebuild months from now starts from the same bytes instead of whatever those tags drift to. No runtime configuration changes.
- **A stored API key that will not decrypt is now an error, not a silent pass-through.** Reading an encrypted secret used to fall back to using the stored value as-is when decryption failed — which is harmless for a key written before encryption was switched on, and wrong for the case that actually happens: rotate or unset `ENCRYPTION_KEY` and every decrypt fails, so raw ciphertext travelled upstream as the bearer token and the provider answered 401. Newly encrypted values carry an `enc:v1:` marker; existing ones are still read. **If you rotated `ENCRYPTION_KEY`, or stored a key that has no recognisable provider prefix before encryption was enabled, re-save it in admin settings.**

- **Request bodies are schema-validated at the handler.** `apiHandler` accepts a body schema that drives both runtime validation and the OpenAPI spec, and the v1 routes that already documented their body schemas now enforce them: an invalid body answers 400 naming the failing fields, and unknown keys are stripped rather than passed through — notably on `PUT /parts/:id`, which previously accepted arbitrary keys.
- **The container boots with migrations, never `push --force`.** The compose app boot runs a guarded `db:migrate` instead of force-pushing schema at start, so a version mismatch can no longer destructively rewrite a live database. **Upgrading operators:** a pre-v0.5 database created by `db:push` must be stamped once with `npm run db:baseline` before the container will boot against it.
- **Two request fields the server never stored are no longer documented in the v1 API.** They are `rationale` on `PUT /api/v1/requirements/{id}` and `taskType` on `PUT /api/v1/tasks/{id}`. Requests that send them behave exactly as before — the values were always discarded — but a generated client will no longer offer them as inputs. `docs/api/README.md` records the narrow exception this falls under: an optional request-body property the server has never stored may leave the v1 snapshot without cutting v2.
- **`POST /api/v1/items/batch-create` naming a branch that does not exist now fails the whole batch with 404**, where before that one row landed in the response's `errors[]` and the call returned 207. Verifying access has to happen before any row is written, which means resolving the branch first; this is the same trade `POST /api/v1/items` has always made. A batch naming a design that does not exist is unchanged in kind — a missing design and one you may not reach answer alike, deliberately.
- **Every v1 request body is now schema-validated.** The remaining 103 handlers that read `await request.json()` by hand — change orders, workflows, work orders, work instructions, designs, programs, users, auth, files, items, parts, requirements, tasks, issues, documents, branches, branch items, relationships, MBOM, reports, software, SysML, import, setup, admin, AI and thread routes, — declare a `body:` schema instead. Unknown keys are stripped, an invalid body answers 400 naming the fields that failed, and the OpenAPI document describes what each route actually enforces; several hand-rolled checks became schema shape on the way, so the 400 names the field rather than restating the rule in prose. One handler still parses its own body, deliberately: `PUT /api/v1/items/:id` cannot choose a schema until it knows the stored item's type. Authorization that used to run as the handler's first statement moved to a declared `access:` hook, which runs after the permission check and before the body parse — so a caller who may not touch the row still answers 403, not a 400 describing a body they were never allowed to send. **For integrators:** bodies that were quietly tolerated before — an unknown field, a wrong-typed value, a required field the handler defaulted — now answer 400.

### Removed

- **The parts inventory columns are gone.** `quantity_on_hand`, `reorder_point`, `location`, and `last_inventory_check` are dropped from the parts table, along with their report fields, work-instruction parametric attributes, and usage-inheritance entries. Mutable stock state was never written by any API surface, and it belongs to the ERP, not a versioned engineering row — Cascadia tracks identity and genealogy, not quantity and value. **Upgrade note:** the migration drops the columns irreversibly; anyone who populated them by hand should export first (`SELECT item_id, quantity_on_hand, reorder_point, location, last_inventory_check FROM parts WHERE quantity_on_hand IS NOT NULL OR reorder_point IS NOT NULL OR location IS NOT NULL OR last_inventory_check IS NOT NULL`). Saved report definitions referencing the removed fields still execute — the dead column is skipped.

### Security

- **Items named in a request body are program-scoped too.** The by-id sweep closed the gap where knowing an id was enough, but it reached only items named in the _path_. A route that links, allocates or relates one item to another names the far end in its body, and every one of them charged only the near end — so a caller holding the verb in their own program could name any item id on the instance as the other end of a write, and the response distinguished a real id from a fabricated one. `POST`/`DELETE` on the requirement satisfy, verify and allocate routes, `POST`/`DELETE /parts/:id/validate`, `POST /items/:id/relationships`, and `POST /relationships/batch-create` now check every item their body names; a `branchId` in a body goes through the same branch check the path routes use. Sharpest of the set, `PUT` and `DELETE /relationships/:relationshipId` address an edge by an id that names neither end, so the blanket `parts` permission was the entire gate — both ends are now charged. Found by [Artur Klujewski](https://github.com/Kujoo25) in [Cascadia-App#85](https://github.com/Cascadia-PLM/Cascadia-App/pull/85).
- **An API key can no longer manage API keys.** A key may be scoped to less than its owner holds, but key management itself accepted any credential — so a narrowed key could mint a second key carrying its owner's full roles (creation scopes against the owner, not the calling credential), learn a broad key's new secret by rotating it, or re-enable a key an administrator had just disabled. Each recovers exactly the authority the scope was meant to remove. Key management, the instance-wide key policy, and the self-service password change are now session-only, declared per route as `authMethod` rather than hand-checked, and an API key attempting any of them is refused. Machine callers that manage keys must sign in instead. Contributed by [Artur Klujewski](https://github.com/Kujoo25) in [Cascadia-App#84](https://github.com/Cascadia-PLM/Cascadia-App/pull/84)
- **An instance can no longer be left with no administrator.** Deleting an account, deactivating one, and reassigning roles were each unguarded, and each is one-way: once the last Administrator is gone, nobody left can undo any of the three, and the repair is a hand-written database statement. All three now take the acting user and refuse to remove the actor's own access, to delete the last Administrator account, or to leave no _active_ Administrator — an inactive one is not cover for removing the one who can still sign in. They read that state under a lock on the shared Administrator role row, so two concurrent requests cannot each see two administrators and remove one. Account status also leaves the generic user update: deactivating has to revoke the account's sessions and is gated on `users:manage`, so `PUT /users/:id` no longer accepts `active` and refuses a body naming it rather than silently ignoring it. Contributed by [Artur Klujewski](https://github.com/Kujoo25) in [Cascadia-App#85](https://github.com/Cascadia-PLM/Cascadia-App/pull/85)
- **Two list endpoints returned data from every program to any authenticated user.** The editable change-order picker and the design-family picker are now bounded by the caller's program membership, like every other collection, and each refuses a filter naming a program or design the caller cannot reach.
- **AI and MCP write tools now check the permission for the item they are actually writing.** Updating any item through the assistant required `parts:update` whatever the item's type, and transitioning any item required `change_orders:update` — so a grant on one item type carried authority over every other. Each now requires that item type's own `update` permission, matching the REST API.
- **Every core collection route is now covered by an enumeration ratchet.** A test proves, route by route, that a user outside a program is served none of that program's items, designs, files, change orders, work orders or physical parts, and any collection route added later is enumerated automatically.
- **Account lockout is now enforced by a single shared policy that every password check goes through,** rather than only the sign-in path, and failure events record which prompt they came from.
- **AI write tools now require a server-issued confirmation token.** The preview-then-confirm flow used to trust a model-supplied `confirmed: true` — any agent, or a prompt injection steering one, could execute a write on its first call with no preview shown. The preview response now carries a single-use token bound to the user, the tool, and the exact previewed parameters; execution redeems it atomically within a short expiry, so the confirmed call must be the call that was previewed. A reused, expired, altered-parameter, or missing token yields a fresh preview — old clients still sending `confirmed: true` degrade gracefully rather than erroring. Honest scope: this proves the preview happened; surfacing it to a human remains the client's contract.
- **Every by-id API surface now enforces program membership.** The authorization sweep closed the gap where knowing an id was enough: item routes and all nine type-specific route files, change orders (including the workflow-transition choke point), the file vault's by-id endpoints, the by-filename lookup, and the relationship graph all verify design/program access before answering — and the graph prunes nodes the caller cannot see instead of leaking their names. A non-member now receives 403/404 where data used to flow, a soft-deleted file answers 400 on its metadata and version routes, and an enumerating invariant test walks every by-id route so a new endpoint fails CI the day it lands ungated.
- **The relationship-graph endpoint caps its query parameters.** Depth and breadth are validated and bounded, closing an unbounded-traversal denial of service that let a single request walk an arbitrarily large subgraph.
- **The file list no longer reaches outside the caller's programs.** `GET /api/v1/files` — the vault browser's listing — was gated on `documents:read` alone and answered with every file in the instance, so a user could read the names, sizes, uploaders and item numbers of another program's drawings without ever needing a file id. It is now bounded to the designs the caller can reach, the same boundary the by-id file routes enforce. A user holding cross-program authority still sees everything, and files on items that belong to no design (tools, work orders) stay visible to everyone, as they do everywhere else.
- **BOM structure is no longer readable across the program boundary.** `GET /api/v1/relationships` took the design to list from the query string and answered with every relationship in it — which parts an assembly is built from, and in what quantity — behind `parts:read` and no membership check at all. It now requires access to the named design, exactly as every by-id item read does. Cross-program authority is unaffected.
- **A part's approved-manufacturer list is now bound to its program.** The AML routes — list, attach, requalify, detach — had no instance-level access check at all, so `parts:read` disclosed any part's qualified suppliers and `parts:update` let anyone rewrite them, across programs. All four now require access to the design the part lineage belongs to. The manufacturer/MPN catalog itself stays instance-global on purpose: like the standard library, a manufacturer and its part number are shared reference data rather than any one program's.
- **The AI assistant and MCP server no longer read across programs by item id.** `get_item_details` scoped its by-_number_ lookup to the caller's reachable designs, but its by-_id_ branch — and `get_bom`, `get_where_used` and `analyze_change_impact`, which take an id and nothing else — did not, so a chatbot user or an external agent holding `parts:read` could pull any program's item, its bill of materials, and its where-used tree by knowing a UUID. All four now check design reach first, on both surfaces. Traversal results stay gated at the root, matching the REST relationship routes.
- **The SysML element-create endpoint now respects item-type permissions and API-key scope.** `POST /api/v1/sysml/projects/:id/branches/:bid/elements` creates real Cascadia items, but declared no permission — so a role without the create verb (View Only, Approver) could mint items through it, and an API key scoped to read-only carried full write access there because key narrowing only applies where a permission is declared. The check now runs on the item type the element maps to, so a role with `tasks:create` can post an ActionUsage and not a PartUsage.
- **The AI assistant can no longer be pointed at another program's API key or budget.** `POST /api/v1/ai/chat` took `programId` from the request body and used it to load the provider configuration — which is where the API key and the monthly token ceiling live — to scope the session, and to attribute the usage row. Nothing checked membership, so a non-member could spend another program's key, exhaust its budget against it, and read its name back out of the assistant's system prompt. The program is now taken from the session for an existing conversation, and checked against membership for a new one; the same check applies to creating a session and to reading a program's AI settings. A chat with no program at all is still allowed and resolves to the instance-wide configuration and budget, which is the administrator's own.
- **Work orders with no program are no longer visible to everyone.** A work order's access is scoped by the program it names, but a work order with no program fell through that check entirely — and because the create form had no program field, every work order created through the UI had none. Anyone who could read work orders could therefore open, edit, run the traveler on, sign off, consume material against and record production for those orders, regardless of program. A work order with no program is now reachable only by users with cross-program authority (`programs:manage`), matching the rule already applied to a change order with no linked designs, and new work orders inherit the program of the part being built. The create form gained a Program field, required when no part is selected. On upgrade, a migration fills in the program for every such work order whose part identifies one — `part_id` to the part's design to that design's program, the same derivation new work orders now use. What it cannot derive it leaves alone: an order with no part, a part in no design, and a part in the Standard Library or any other program-less design stay unset, and those remain visible to holders of `programs:manage` alone for an administrator to assign. The migration never guesses a program, it only restores one the row's own part already implied, and it fills blanks only — an order an administrator has already assigned keeps that assignment.
- **A change order can no longer be advanced by someone who can only see part of it.** Submitting, releasing or cancelling an ECO now requires access to every design it links, not just one of them. Reading one is unchanged — the designs you cannot reach are still redacted, and `hasRestricted` still says something was withheld — but the transition endpoint used to accept the read rule while a release merged every linked design's branch and assigned permanent revision letters across all of them. A member of one program could therefore stamp revisions into another program's designs; a cancel could archive branches, discarding in-flight work, on the same authority. The affected-items panel and the ECO summary already told users an ECO in this state could not be submitted or released — now the server agrees. Advancing such an ECO returns 403; the remedies are program membership or an Administrator, both immediate and neither touching data.
- **A work instruction reorder can no longer renumber another work instruction's operations.** Reordering operations issued an UPDATE scoped on the row id alone, so a user authorized to edit one work instruction could name any other instruction's operation ids in the request and rewrite their ordering — across programs, branches, and released versions, bypassing the target's own edit lock. The reorder is now scoped to the work instruction being edited; ids belonging to anything else are ignored.
- **Task and Requirement endpoints now check their own permission, not the Parts one.** The by-id read, update and delete routes under `/api/v1/tasks` and `/api/v1/requirements` were gated on the `parts` resource, so a custom role or API key scoped to `tasks` or `requirements` was wrongly refused them, while one scoped only to `parts` could reach them — even though the generic item route already gated the same rows correctly. They now check `tasks` and `requirements`. No built-in role is affected: all five grant the same read, update and delete across the three resources. Separately, deriving a child requirement (`POST /api/v1/requirements/:id/derive`) creates a real item but declared no permission at all, so role checks were skipped and API-key scope narrowing had no effect on it; it now requires `requirements:create`, which the built-in Approver and View Only roles do not hold, matching what the generic item-create route already enforced.
- **Requirement traceability endpoints now check their own permission.** Creating and removing satisfaction, allocation and verification links declared no RBAC tuple, so role permissions were skipped entirely and a read-only program member could rewire any requirement's traceability graph; they now require `requirements:update`, and the matching reads require `requirements:read` so API-key scope narrowing applies. The item thumbnail endpoint now resolves the item's own resource instead of always charging `parts`.
- **The part a work order names is now checked against the caller's reach on both create and update.** Filing or repointing an order at a part in a program you cannot open is refused, so the response no longer echoes that part's number, name and revision back — and the traveler can no longer be populated from another program's BOM and work instructions through it. A part and a program that name different programs are refused together for the same reason; a part in the Standard Library or an unassigned design has no program of its own and stays buildable from any of them. Integrators see 403 where a body named an unreachable part, 404 rather than 500 where it named one that does not exist, and 400 where the part and the program disagree.
- **The item list no longer hands over rows the type's own access gate refuses.** `GET /api/v1/items` admitted any item with no design to every caller, on the reasoning that such an item sits outside every program. That is true of a tool; it is not true of a work order, which names its program on its own row, or of a physical part, which is an instance of a part that lives in a design. So a work order the work-order list hid and the by-id read refused was still listed here, to anyone holding the read permission a stock viewer role carries. Work orders now scope on their program and physical parts on their part's lineage, on every surface that shares the boundary — the item list, search, dashboard counts, saved reports and the vault listing.
- **`GET /api/v1/items/by-filename/:filename` decided the caller's scope after fetching, not before.** It read every matching file and item row unbounded and then filtered in memory, which handed over every change order in the instance — an ECO's designs hang off a link table, so its own design is always empty — and let any authenticated account ask for a full scan of the file table as often as it liked. The scope is now part of the query, the result is capped and reports when it was, soft-deleted items no longer answer, and the route has its own rate limit.
- **Four item-detail writes now charge permission on the item's own type.** Adding a relationship, syncing properties, and taking or releasing an item lock declared no permission requirement at all, so a role's grants were never consulted on them and a scoped API key had nothing to narrow. Program membership was the only gate, and membership is checked through the item's design — which work orders and physical parts do not have, so syncing properties onto one of those was open to any signed-in account, renaming it and writing its state directly past the lifecycle rules. Each of the four now requires update permission on the item's own type, dispatched per type so a document is charged against documents and a part against parts. A View Only member can no longer rename an item, force its state, add relationships to it, or take its lock; a standard User keeps all four everywhere except on change orders, which that role has never been able to update.
- **Breaking another user's item lock now requires `system:manage`, matching stealing one.** `POST /api/v1/items/:id/unlock` accepted `force: true` from any caller holding the item type's `update` permission, while the mirror override on `POST /api/v1/items/:id/lock` charged `system:manage`. A forced unlock followed by an ordinary lock therefore reached the lock route's administrator-only end state — previous holder evicted, item held by the caller — without the administrator grant. Power User, Approver and User roles lose the ability to evict a peer's lock; Administrator is unaffected, as is releasing a lock you already hold (with or without `force`) and the no-op response on an item that is not locked. API keys must now carry both the item type's `update` and `system:manage` in scope to force an unlock.
- **Every read on `/api/v1/items/:id/*` is now gated by program membership, and charges a permission tuple dispatched on the item's own type.** `GET /:id/at-context`, `GET /:id/available-contexts` and `GET /:id/history` checked only `items.design_id`, which is NULL on every change order and on issues scoped by program — so on those types authentication was the entire gate, and `at-context` returns the change order row in full. All three now call the same instance gate as the rest of the file. Eight reads — those three plus `POST /:id/impact-analysis`, `GET /:id/lock-status`, `GET /:id/relationships`, `GET /:id/satisfied-requirements` and `GET /:id/where-used` — additionally charge `read` on the path item's own resource, which they declared nowhere before, so role permissions were never consulted and a scoped API key had nothing to intersect against. On work orders and physical parts that tuple closes an authentication-only read of consumption and production edges, unit genealogy, lock status and satisfied requirements. No shipped role loses anything: every role holds `read` on all thirteen item types. Two consequences worth knowing — a program boundary is still not restored for work orders and physical parts through these routes, which needs a dispatch the instance gate does not have yet; and because the gate now runs ahead of the existence lookup, an id that is both soft-deleted and out of reach answers 403 rather than 404.
- **`POST /api/v1/items/batch-create` now checks design and branch access before it writes anything.** The route charged only the per-type create verb, which is instance-blind, and then handed the caller's own data to the item service, which does not check membership on create. Any caller holding `parts:create` could write rows into another program's design, or into one of its branches, knowing nothing but an id — the branch path being the sharper one, since it takes the design from the branch and ignores whatever the body says. The stock Power User and User roles both reached it. The check runs once over the whole batch before the first row is written, so a mixed batch is refused whole rather than half-applied. Creating a change order through this route is now refused, as it already was on `POST /api/v1/items`: an ECO is defined by the designs it touches and neither route can take them, so one created there was linked to nothing. Create them via `POST /api/v1/change-orders`.
- **The generic `/items/:id` router now scopes work orders and physical instances.** `requireItemAccess` dispatched change orders and issues and then fell through to a design check, and neither a work order nor a physical instance carries a design — so that arm passed vacuously on 31 generic sub-routes plus the AI and MCP tool handlers, while the item list and both typed routers refused the very same rows. A work order is now authorized on the program it names, a physical instance on the design of the part lineage it instantiates. Three routes that hand-rolled the design check move to the same dispatch, which closes their change-order and issue halves too, and one of them — model versions — gains a read permission it never declared at all. A work order with no program stays reachable by cross-program authority alone, so an administrator can still open it and set one; an instance whose lineage carries no design stays ungated, unchanged and now pinned by a test. One status change, the same trade the item-detail reads already made: an id that is both soft-deleted and out of reach answers 403 rather than 404.
- **The physical-instance index no longer lists every serial and lot in the instance.** `GET /api/v1/physical-parts` ran with no access scope at all, and all five built-in roles hold `physical_parts:read` — so one request returned every serial number, lot number, ERP reference, technician note and resolved part name in the database to any signed-in account, which is as-built manufacturing data reachable by opening a sidebar page. It is now bounded by the caller's accessible designs, using the same predicate the item list already scoped this type on, so the two surfaces cannot answer one question two ways. The recall query is bounded on the same axis — its part filter enumerated a whole lineage together with the end items each unit was built into — and registering an instance now checks the part lineage named in the request, which previously disclosed whether a part existed, and with what tracking mode, to anyone holding `physical_parts:create`. Instances whose part lineage sits in no program stay visible to everyone, unchanged.
- **The AI assistant and MCP server no longer write across programs.** `create_item`, `create_relationship` and `transition_item_state` were gated by type-level role permissions alone, and none of the services behind them draws the program boundary — so a chatbot user, or an external agent holding ordinary `parts` grants, could plant an item in another program's design (naming it by id or by design code), hang one program's part off another's assembly, or drive a foreign item through its lifecycle states, knowing only an id. All three now check design, change-order and item reach first, and check it _before_ the confirmation preview, which otherwise echoed the design's name, the two item numbers and the current state back to the caller. `update_item` was already gated by `ItemService.update`; cross-program authority is unaffected. This is the write-tool sibling of the read-tool fix above.
- **Rate limiting and authentication-event logging no longer trust a spoofable `X-Forwarded-For`.** Both keyed off the leftmost entry of a header any caller can set, so a client could mint a fresh login rate-limit bucket per request, spend someone else's budget, or forge the address written into the audit trail. The client address is now resolved through a trust-aware path that believes a forwarded header only as many hops deep as `TRUSTED_PROXY_COUNT` declares — default `0`, trusting none, which is correct for a directly-exposed deployment and must be raised to match the number of proxies in front of one. `RATE_LIMIT_ENFORCE=true` opts a non-production deployment into enforcement.
- **The global search box no longer returns item types the caller may not read, and its `limit` is bounded.** `GET /api/v1/enterprise-search` — the header typeahead — searched every registered item type and applied only the design-level scope, so a role that withholds read on a type still saw that type's rows grouped and labelled, while the `/results` grid behind the same search page refused them. The typeahead now searches only the types the caller may read, exactly as the grid does, and a caller with no read grants gets nothing rather than the whole registry. Its `limit` was an unvalidated `parseInt` with no ceiling: it now takes the same bounds the grid uses (1–100, defaulting to this endpoint's own 50), so an oversized limit and a non-numeric one answer 400 instead of an unbounded query and the silently empty groups a `NaN` limit used to produce.

## [0.5.0] - 2026-08-25

### Added

#### Physical Traceability

Identity and genealogy for real material, without crossing into quantity or value —
no inventory balances, no costing. See
[docs/features/physical-parts-and-traceability.md](./docs/features/physical-parts-and-traceability.md).

- **PhysicalPart item type** — A physical instance of a Part: a serialized **unit** or an identified **lot**. Non-versioned (Tool pattern). It accumulates documents in the vault (material certs, test reports, CoCs), carries requirement evidence, and anchors genealogy. Numbered `PP-000001` as a stable handle; the display identity is the serial or lot number, unique per part lineage
- **Work Orders promoted to an item type** — Previously a standalone table. As items they hold vault attachments and participate in `item_relationships`, and keep the same `WO-000001` numbering so migrated and new numbers are indistinguishable
- **Consumption, production, and evidence as edges** — `Consumes`, `Produces`, and `Evidences` records in `item_relationships`, with the work order or physical part always the edge source. Consumption pins quantity to the consumed revision
- **Derived genealogy** — Never stored. `GenealogyService` walks the edges on demand, so it cannot drift from the records it summarizes. Forward (`/:id/genealogy`) and reverse (`/physical-parts/recall`) traversal
- **Qualification rollup** — `GET /api/v1/work-orders/:id/qualification` answers "were these requirements satisfied?" for a build: requirements in scope via `Satisfies` edges from the built part and every consumed material's lineage, satisfied where an `Evidences` edge matches, plus a gap list of consumed instances carrying neither evidence nor documents
- **Approved Manufacturer List** — `manufacturer_parts` and `part_manufacturer_parts`, bound to the part `masterId` so the AML survives revisions. Replaces the unwired COTS tables
- **Part `trackingMode`** — `none`, `lot`, or `serial`, the policy that decides whether a part's instances are tracked and how

#### Work Instruction Traveler

- **Work instructions are templates, never executed directly.** A work order instantiates them as traveler lines (`work_order_instructions`), each a frozen content snapshot with a `requiredCount` of runs; executions (`instruction_executions`) record runs of lines, and sign-offs ride executions. Line status is derived from countable runs, work-order completion is gated on the traveler, and skip-with-reason is the audited escape hatch. Snapshots freeze permanently once a line has executions

#### Software Management

Firmware and software configuration items versioned alongside the hardware they
ship with. See [docs/features/software-management.md](./docs/features/software-management.md).

- **Software item type** — `softwareType` (firmware, application, library, configuration, fpga), target hardware, toolchain, and a build-artifact slot in the vault. Shares the Part lifecycle, so it is ECO-controlled like any other released engineering item
- **Content-addressed source store** — `software_blobs` plus immutable `software_manifests`. The `manifestId` pointer rides the item version, so branch isolation and time travel work with no special cases
- **Checkout-gated editing** — Edits accumulate in `draftManifestId` and are promoted by an explicit commit, which records per-file `source`-category field changes. Drafts are never copied to new versions and never appear in field history
- **Per-file conflict granularity** — `ConflictDetectionService` sharpens software manifest conflicts from "the manifest changed" to the specific files that diverged

#### Optional Package Framework

- **Package framework** — The mechanism by which separately-licensed functionality is gated, via the `CASCADIA_PACKAGES` environment variable, read once at process start. `PackageRegistry` answers entitlement, `requirePackage()` gates server-side with a 403, and `/admin` lists holdings read-only. There is deliberately no in-app toggle. The framework ships in this edition; the packages that plug into it are licensed separately. See [docs/development/adding-packages.md](./docs/development/adding-packages.md)

#### Release Readiness

- **Migration baselines and a real upgrade path** — the edition ships its `0000` baseline under `apps/cascadia/drizzle/`. The new `npm run db:baseline` stamps a pre-0.5, push-created database — after verifying its schema actually matches — so `npm run db:migrate` takes over from there; running it on a database that is not at the baseline refuses loudly. CI gains a drift gate: a schema change cannot land without its committed migration. See [docs/deployment/upgrading.md](./docs/deployment/upgrading.md)
- **The running version is identifiable** — `GET /api/v1/health` reports it, the admin page shows it on a System card, and images carry `org.opencontainers.image.version`/`.revision` labels from build args. Previously the version existed only in package.json, making a deployed instance impossible to identify from outside
- **XLSX import templates** — `format=xlsx` on the parts/documents/issues template endpoints returns a real workbook; an unrecognized format is a 400 instead of a silent CSV fallback

#### File Preview

- **SVG drawings preview in the app** — The vault has always accepted `.svg` uploads but refused to render them, because an SVG is a scripting host and preview bytes are served from the app's own origin. SVG is now its own `PreviewKind` with a zoom/rotate/pan/fullscreen viewer, and three properties hold that boundary together, all of which have to be true at once: the server labels the bytes `text/plain` rather than `image/svg+xml`, so a browser reaching the endpoint directly renders source; the viewer draws through an `<img>`, which the SVG spec puts in secure static mode; and the `<img>` source is a `data:` URL rather than an object URL, which would carry the app's origin into a new tab. Nothing is sanitized and nothing needs to be — a hostile drawing's `<script>` and its external `<image href>` both survive in the source and neither executes nor fetches. Thumbnails and the gallery still refuse SVG outright
- **Per-format preview ceilings** — `PreviewFormat` gains an optional `maxBytes`. SVG caps at 8 MB against the global 50 MB, because the data URL roughly doubles the source and has to be built as a single JavaScript string, so past that point the viewer rather than the transfer is what gives out

#### User Management

- **Password change from the profile page** — A signed-in user with a local account can change their own password (`PUT /api/v1/auth/password`). The current password is verified first, the request is rate-limited like a login attempt, and API-key callers are refused outright — a key must not be able to replace the interactive credential of its owner. Every other session is signed out in the same transaction as the change, keeping only the one that made it, and a `password_changed` auth event is recorded. Contributed by [Artur Klujewski](https://github.com/Kujoo25) in [Cascadia-App#71](https://github.com/Cascadia-PLM/Cascadia-App/pull/71)

### Fixed

- **BOM line quantities are editable, defaulted, and honest on branches.** Four related defects, found in release testing: the add dialog showed "1" as a placeholder but submitted nothing, so untouched BOM lines were created with a null quantity (lines now start at a real 1 and require a positive decimal — the column is numeric(10,3)); quantities could not be edited at all afterward (a new edit dialog drives `PUT /api/v1/relationships/:id`); in a branch context the relationship read returned the union of the working copy's and main's edges, so a line deleted on the ECO branch reappeared as main's row — deleting that one tripped `BRANCH_PROTECTED`, and with a quantity set the failure looked like it had merely cleared the quantity (the read now follows the merge's authority rule: the working copy's edges are the structure); and the confirm dialog dismissed the very error alert a failing action had just opened, so rejections now stay visible and carry the server's reason
- **Every version row carries its BOM edges.** Working copies minted by a field-only first save or a rebase carried no relationship rows and leaned on a zero-edge fallback to main — which made an intentionally emptied structure indistinguishable from an unpopulated copy: deleting the last BOM line resurfaced it read-only, and releasing re-shipped it. Every copy path now carries relationships the way it already carried files, the fallback is gone, and no edges means no edges: an emptied structure reads and releases as empty

- **The password dialogs always failed.** `PUT /users/:id/password` requires the current password, but both UI callers sent only the new one, so every attempt was a 400 — including the change README and SECURITY.md instruct operators to make to the default admin credential. Admin password-setting now goes through `reset-password` (the operation that never needs the target's current password), self-service goes through the new `/api/v1/auth/password`, and `docs/deployment/single-server.md` no longer claims the default password is `admin` (the seed creates `Cascadia`)
- **The E2E lifecycle suite can no longer pass by vacancy.** Eight lifecycle tests skipped themselves when no design was seeded, so a seeding regression produced a green suite that had tested nothing. Global setup now guarantees a selectable design and the specs assert it
- **`analyze_change_impact` failed on every item it was asked about**, over
  both the in-app chatbot and the MCP server. The tool includes related change
  orders by default, and having no current ECO to exclude it passed `''` as
  one; `findRelatedChanges` renders that argument into a uuid comparison, so
  Postgres rejected the whole statement (`22P02`) rather than matching nothing.
  Only `includeRelatedChanges: false` ever returned an answer.
  `currentChangeOrderId` is now optional and the `!=` predicate is dropped when
  it is absent — which is what "no current change order" should have meant all
  along: every open ECO touching the item

- **The dev MCP server's docs and database tools resolve against the repository
  root again.** `REPO_ROOT` counted `..` segments up from
  `lib/mcp/dev-tools.ts`, which reached the repository root before the
  `packages/core` move and `packages/core` after it. The failure was silent:
  `search_docs` reported `filesSearched: 0` for every query, `read_doc`
  returned ENOENT for every path, and the `db_*` tools would have run their
  npm scripts from a directory holding no `scripts/`. The root is now found by
  walking up to the manifest declaring `workspaces`, which identifies it by
  what it is rather than by how deep the file sits. The corrected root also
  exposed `db_push` running bare `npx drizzle-kit push`, which fails on a
  missing config because drizzle-kit must be launched from the edition's app
  directory — it goes through `npm run db:push` like every other database
  tool. Separately, `instance_status` read `process.env` before anything
  imported dotenv, so it reported `DATABASE_URL` unset in the same response as
  a successful database connection; the entry point now loads the root `.env`
  first, resolved from the repository root rather than the working directory
  an MCP client happens to choose

- **The AI and MCP write tools no longer advertise field values the server
  rejects.** `create_item`'s `requirementType` enum offered `Interface`,
  `Constraint` and `Other` — none of which the Requirement item type accepts —
  while hiding four it does (`Non-Functional`, `Security`, `Usability`,
  `Business`). The handler copies the value straight into the item, so a
  request for any of the three failed validation inside `ItemService` and
  surfaced as a bare `Validation failed` carrying no field name and no
  accepted values, which an agent cannot self-correct from. Every enum in the
  write tools is now the Zod enum exported by the item type that validates the
  write — the derivation `itemType` already used — which also caught task
  `priority` (advertised lowercase against a capitalized enum, so every value
  was rejected by `create_item` and written unvalidated by `update_item`) and
  `changeType` (missing `XCO`, which the UI has always offered). A failed
  write now names the offending field instead of reporting a bare
  `Validation failed`

- **`@xyflow/react` pinned to `12.11.2`.** `12.11.4` imports
  `handleAttributionWarning` from `@xyflow/system`, which its own pinned
  `@xyflow/system@0.0.80` does not export, so a fresh install resolving the
  previous `^12.9.3` range could not build the client bundle

- **An item's design can no longer be cleared or reassigned through update.**
  `ItemService.update()` wrote `designId` straight through whenever the key was
  present, so a request carrying `"designId": null` detached the item from its
  design while its branch rows, commits and BOM structure stayed behind, and
  reassigning it landed the item in a design whose branches had never tracked
  it. Both now raise `VALIDATION_FAILED` (400). The guard lives in the service,
  so the type-specific update routes, the batch update, the AI update tool and
  the import paths share it. An echoed unchanged value is still accepted —
  whole-object form saves send one — and assigning a design to an item that has
  none is still allowed, being the one direction that adds history rather than
  orphaning it
- **The requirement derive hierarchy follows revisions.** `parent_requirement_id` names one version row of the parent — whichever was current when the child was derived — and nothing ever re-points it, so once a parent had been revised through a change order both directions inverted: the current parent row returned no children at all, the row it superseded returned every historical row of every child, and a current, Released child reported a superseded, Draft parent. Both reads now resolve through shared lineage primitives in `lib/items/version-lineage.ts`, so the relationship edge table and this pointer column answer to one rule rather than two. Derived numbering also takes the highest `-D<n>` already used rather than the count, which was only ever right while nothing had left the tree
- **Item links resolve through the route map instead of naive pluralization.** Twelve components built item URLs by appending "s" to the lowercased item type, which is wrong for 7 of the 13 types — Software linked to `/softwares` while the route is `/software`, and change orders, test plans, test cases, work instructions, work orders and physical parts all 404'd the same way. Each carried its own partial copy of the map and invented a different fallback for the types it did not cover: either a route that does not exist, or a parts page rendered against a foreign id, which loads and is therefore harder to notice than a 404. A new `ItemLink` component now carries the "link when routable, plain text otherwise" policy, and the few non-link sites drop their View entry when there is no route. An item type added without a detail page renders unlinked rather than pointing at a parts page
- **The 3D viewer no longer fetches its environment map from a third-party CDN.** It rendered a drei `<Environment preset>`, which resolves the preset name to an HDR hosted on a public CDN and fetches 1–2 MB at runtime — in an app expected to run air-gapped. The failure also outlived itself: `useLoader` memoizes a rejection exactly as permanently as a result, so one unreachable fetch made every later mount of the viewer re-throw during render, past `<Suspense>` — which catches suspension, not errors — and into the root error boundary, replacing a part's Details page with "Something went wrong" until a full reload. The environment is now a local rig of `<Lightformer>` panels, which renders a cube map in place and leaves no fetch path to fail, and the canvas has its own error boundary so a scene that cannot draw costs the preview rather than the page
- **A failed file preview reports the error instead of a literal "[object Object]".** The error body was read as `{ error, details }` when the envelope is `{ error: { code, message } }`, and the `details` it surfaced is the internal vault path on a storage miss
- **Re-seeding no longer downgrades an already-upgraded lifecycle.** `seed-minimal.ts` hand-wrote most of the shipped lifecycles at version 1 with unconditional upserts and only then called the module. A fresh reset came out right, because the module's newer rows won afterwards, but a plain re-seed over an existing database handed an already-upgraded row its old shape while leaving the version number in place — after which the module's upgrade-only gate refused to repair it
- **A lookup by item number no longer answers from an arbitrary design.**
  `ItemService.findByNumber` was an unordered `LIMIT 1` with no design scope,
  and item numbers are not unique — creating an MBOM copies an engineering
  design's items into a Manufacturing design keeping their numbers, and a usage
  repeats its definition's number in every design that uses it. Which row came
  back was whatever the query planner reached first, in practice the
  manufacturing copy: `get_item_details {"itemNumber": "USV-1900"}` returned the
  empty revision `-` Draft shadow instead of rev B Released, so an assistant
  asked what was in the harness answered "nothing", with nothing in the response
  to suggest it had been handed the wrong row. Matching rows are now put in a
  total order — engineering before library before manufacturing, then released
  lineage before drafts, then newest, then id — so the same database always
  yields the same item; release state is asked of `LifecycleService` rather than
  compared against a literal. `findByNumber` and `get_item_details` take an
  optional `designId` (a UUID or design code, as `search_items` already
  accepts), and where a number is still ambiguous the runners-up come back as
  `otherMatches`, each named by its design, so an assistant can ask which design
  was meant instead of guessing silently. Every `get_item_details` response now
  also carries the design's code, name and type

- **Password reset from the admin user pages works.** The reset dialog posted
  to the verified-change endpoint, which demands the account's current
  password; the dialog never collected one, so every attempt was rejected as
  invalid credentials and an administrator could not reset any password at all.
  Reset is now its own endpoint — `POST /api/v1/users/:id/reset-password`,
  gated on `users:manage` and rate-limited like a login — the dialog calls it,
  every session of the target account is revoked, and a `password_reset` auth
  event records the acting administrator. Contributed by
  [Artur Klujewski](https://github.com/Kujoo25) in
  [Cascadia-App#71](https://github.com/Cascadia-PLM/Cascadia-App/pull/71)
- **Deleting a user no longer fails once the account has any history.**
  `deleteUser` removed the role links, then the user row — and every other
  reference, including the auth events written by simply logging in, raised a
  foreign-key violation that surfaced as an unhandled 500, so no account that
  had ever been used could actually be deleted. Deletion now runs in a
  transaction that locks the row, clears the account's own auth history, and
  lets the account-owned rows cascade; when business records still reference
  the user, it rolls back and deactivates the account instead — sessions
  revoked, history intact — and reports which of the two happened, so the UI
  can say so. Contributed by [Artur Klujewski](https://github.com/Kujoo25) in
  [Cascadia-App#71](https://github.com/Cascadia-PLM/Cascadia-App/pull/71)

### Security

- **Assistant tool errors no longer hand the model the failed SQL and its
  bound parameters.** Both surfaces that run PLM tools — TanStack AI for the
  chatbot, the MCP server for external agents — put a thrown message straight
  into the tool result the model reads, and drizzle's query wrapper _is_ the
  statement plus every parameter value. Database failures now collapse to a
  generic sentence and keep their detail in the server log. Not-found,
  validation and permission messages survive untouched, being exactly what the
  model needs to correct course

- **An unset `ENCRYPTION_KEY` stores provider API keys as plaintext, and now
  says so.** AI provider keys entered in the admin UI are encrypted with
  AES-256-GCM only when `ENCRYPTION_KEY` is set. Without it they are written to
  the database in the clear, and nothing surfaced that: a working integration
  looks identical either way. The storage behaviour is unchanged; what changed
  is that the plaintext path now logs a warning naming the provider (never the
  key), and the variable is documented in SECURITY.md, both compose files, and
  the env examples. Keys saved before `ENCRYPTION_KEY` was configured stay
  plaintext — re-save them once it is set
- **Item-number lookups are scoped to the designs the caller can read.**
  `get_item_details` applied no design scope when resolving an item number, so
  naming a number was the one way to read an item out of a program you are not a
  member of — `search_items` has always filtered by accessible design. The
  by-number path now goes through the same `accessScopeCondition` helper the item
  lists, search and report execution use, which also keeps the new `otherMatches`
  list from becoming a way to enumerate items in designs the caller cannot reach.
  Lookup by an explicit item id is unchanged

- **User reads no longer carry credential material.** Every user object
  leaving `UserService` — lists, detail reads, create and update returns — now
  omits `passwordHash` and `failedLoginAttempts` at the type level rather than
  by caller discipline. Password changes and resets write `auth_events` rows
  naming the actor where one account acted on another, and session revocation
  happens in the same transaction as the credential update, so a failure
  cannot leave a new password live alongside sessions it should have ended.
  Contributed by [Artur Klujewski](https://github.com/Kujoo25) in
  [Cascadia-App#71](https://github.com/Cascadia-PLM/Cascadia-App/pull/71)
